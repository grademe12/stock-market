# Day 3 매칭기 포화 보고서

Day 1에서 한도는 러너 직렬 HTTP였다. 그 다음으로 동시 전송 캡을 열고, 틱·주문 주기를 벽시계로 나눈 뒤, 매칭기 CPU를 어디까지 밀 수 있는지 봤다. 수치는 2026-09-16~09-17 KST Prometheus와 러너 로그다.

**학습 질문**: 러너가 주문을 더 보내면 매칭기 CPU는 포화하는가? 포화하면 처리량은 오르는가, 호가 작업량에 막히는가?

## 1. 측정 조건

| 항목 | 값 |
|---|---|
| Backend | GCE `e2-medium` (2 vCPU, 4 GiB). 샤드 2개(`:8000`, `:8001`). 샤드마다 Gunicorn worker 1 · threads 4, host network |
| 매칭기 | 종목별 인메모리 호가창. 같은 종목의 active replica는 1개 |
| DB | 미니 PC Postgres 17. 주문·체결·잔고는 비영속. 프로필·KRX 일별만 저장 |
| 경로 | 미니 PC 러너 → Tailscale → GCE:8000/8001. GCE → Tailscale → 미니 PC:5432 |
| 관측 | 미니 PC Prometheus/Grafana. 후반에는 Prom/Grafana `network_mode: host`. 러너 `/metrics` `:9101`–`:9105` |
| 시뮬 유니버스 | 10종목, 샤드당 5종목 |
| 트레이더 | noise / momentum / mean_reversion / liquidity_provider. `event_reactive` 0. `MAX_TRADERS=1000` |
| 러너 | 컨테이너 5개(noise 샤드 0·1 + 나머지 전략 1개씩). host network |
| 고정 캡 | `HTTP_CONCURRENCY=64`(실험 중 32·128 비교). `TICK_INTERVAL_MS` 1000 → 250 |
| TTL / 주기 | `order_ttl_seconds`(벽시계). 후반 `interval_ticks` → `interval_seconds` |

`orders/s`는 `POST /api/v1/orders/` 수다. 프로필 수나 틱 수가 아니다. 서버 측 지연은 Django 히스토그램이다. Prometheus 기본 버킷은 0.1s 다음이 0.25s라, p99가 ~220ms 근처에 붙으면 실제 꼬리와 버킷 보간을 구분해야 한다.

## 2. 이틀 동안 바뀐 것

1. 전송 캡을 32 → 64 → 128로 올렸다가 64로 되돌렸다. 128은 한 틱에 더 큰 묶음만 쏟아 Gunicorn 줄을 만들었고, 초당 처리량은 오히려 줄었다.
2. 러너 `/metrics`와 Grafana 패널을 보탰다. Docker 브리지에서 호스트 포트 hairpin이 안 되어 Prom/Grafana를 host network로 옮겼다.
3. `order_ttl_seconds`에 이어 주문 주기 `interval_ticks`를 `interval_seconds`로 바꿨다. 틱을 줄여도 한 사람의 벽시계 주기는 유지된다. 1초 틱에서는 값 1–5가 이미 1–5초라 배포 직후 주문 속도는 거의 그대로였다.
4. `TICK_INTERVAL_MS`를 1000에서 250으로 줄였다. 설정만 줄었고, 틱 한 바퀴 벽시계는 0.7–1초에 남았다. 한 회차 안에서 호가 GET이 동기이고 앞선 주문·취소와 같은 워커 줄을 탄다.
5. 백엔드를 다시 띄우면 메모리 호가는 0이 된다. 09-16 17:12와 19:10 전후에 잔량이 급감했다가 다시 쌓였다. 프로세스를 안 내리면 잔량은 밤새 선형으로 늘었다.

## 3. 부하 숫자

### 3.1 캡 32 · 호가 얇음 (비교 기준)

| 지표 | 값 |
|---|---|
| 주문 POST | ~140/s |
| 프로세스 CPU 합 | ~0.67 |
| POST p50 / p99 | ~3 / ~25 ms |
| 4xx · 5xx | 0 |

코어 여유는 있다. 제공 부하는 캡과 1초 틱에 묶여 있다.

### 3.2 캡 64 · 재시작 직후 얇은 호가 (09-16 17:13 이후, 19:10 전후)

| 지표 | 값 |
|---|---|
| 주문 POST | ~110–140/s |
| 취소 DELETE | ~50–90/s |
| POST p50 / p95 / p99 | ~3.5 / ~50–120 / ~220 ms |
| 프로세스 CPU 합 | ~1.4–1.55 (샤드당 ~0.7–0.78) |
| 호가 잔량 합 | ~0.5만–8만 |
| `runner_http_in_flight` | 틱 직후 대당 64, 합은 13–200을 오감 |
| 4xx · 5xx | 0 |

절반 주문은 몇 밀리초다. p99는 봇이 1초(또는 한 틱)마다 한꺼번에 넣어서 생긴 꼬리다. CPU 1.5/2는 여유 적음이지, 주문을 버리는 상태는 아니다. 슬롯 64는 주문과 TTL 취소가 나눠 쓴다.

### 3.3 캡 128 (짧게)

한 틱 동시 요청만 늘렸다. p99는 ~225ms에 붙고 초당 POST는 64일 때보다 줄었다. 프로필 조회가 타임아웃 난 러너가 있었다. 캡을 키워도 워커는 샤드당 스레드 4개라 줄만 길어진다. 64로 되돌렸다.

### 3.4 틱 250ms (09-16 19:46 이후, 첫 1시간)

| 지표 | 1초 틱 직전 | 250ms 설정 직후 |
|---|---:|---:|
| 주문 POST | ~137/s | ~155/s |
| CPU 합 | ~1.36 | ~1.49 |
| POST p50 / p99 | 3.5 / 220 ms | 3.3 / 218 ms |

사람 주기는 초 단위라 틱을 줄여도 한 사람의 주문 횟수는 그대로다. 러너 로그상 40틱이 약 39초(회차당 ~1초)였다. 타이머 250ms는 일이 끝난 뒤 쉬는 시간일 뿐, 초당 4회가 되지 않았다.

### 3.5 캡 64 · 호가 붕괴 (09-16 밤 ~ 09-17 17:28)

잔량은 09-16 19:26 약 1.1만에서 09-17 17:26 약 190만까지 거의 쉬지 않고 늘었다. POST는 같은 기간 139/s → 19/s, p50은 3.5ms → 291ms.

09-17 17:28 KST 한 점:

| 지표 | 값 |
|---|---|
| 주문 POST | ~17/s |
| 취소 DELETE | ~5/s |
| 호가 GET | ~2/s |
| 체결 `trades_executed` | ~12/s |
| POST p50 / p99 | ~300 / ~900 ms |
| 프로세스 CPU 합 | ~1.90 (0.97 + 0.93) |
| RSS 합 | ~815 MiB (샤드당 ~400 MiB) |
| 호가 잔량 합 | ~190만. 종목·사이드 하나가 9–11만 |
| ready | 200이지만 3–5초 |
| 러너 | 주문·취소·호가 GET `timed out` (`REQUEST_TIMEOUT_MS=5000`) |
| 5xx | 0 |

프로세스는 살아 있다. 권한 있는 주문을 초당 열일곱 건만 받아 내고, 그 일도 수백 밀리초가 걸린다.

## 4. 병목

```text
[트레이더 주기(초)] --벽시계, 틱을 줄여도 유지-->
[러너 틱 한 바퀴] --호가 GET 동기 + 슬롯 64, 회차 ~1초-->
[Gunicorn 줄] --한 틱 폭주 때 p99, 캡 128에서 확인-->
[인메모리 호가] --잔량이 커지면 여기가 본체-->
[CPU 2코어] --잔량 190만에서 1.9로 포화-->
```

### 4.1 얇을 때 한도: 러너가 보내는 양

캡 64·얇은 호가에서 CPU는 1.5 근처, POST는 110–140/s, p50은 3–4ms다. 사람 수를 1000으로 올려도 슬롯이 이미 차면 초당 POST는 늘지 않는다. 캡 128은 같은 회차에 더 많이 넣을 뿐이라 줄만 길어진다.

틱을 250ms로 줄인 이유는 이 빈 시간을 채우기 위해서였다. 실제로는 회차 일이 0.7–1초라 초당 회차는 거의 1에 남았다.

### 4.2 두꺼울 때 한도: 호가 한 건의 비용

미체결 지정가는 설계대로 호가에 남는다. `noise`는 호가를 보지 않고 기준가 근처에 걸고, `liquidity_provider`는 중간가 양쪽에 건다. TTL이 끝나야 러너가 DELETE 한다.

잔량이 늘면 주문 하나(그리고 호가 GET·취소)가 비싸진다. 같은 캡 64인데도 POST가 140/s에서 17/s로 줄고 CPU는 1.5에서 1.9로 올라간다. 코어를 더 쓰는데 처리량은 떨어진다. 취소를 보낼 슬롯도 같은 줄에 있어, 만료가 밀리면 잔량은 더 는다. 09-16 밤부터 09-17 오후까지 잔량 곡선이 거의 직선인 이유다.

백엔드를 재시작하면 메모리가 비워져 3.1·3.2 구간처럼 잠시 회복한다. 러너 설정이 같으면 같은 쌓임이 다시 시작한다.

### 4.3 아직 한도가 아닌 것

- Postgres: 핫패스에 없다. Day 1에서 닫은 상태와 같다.
- 5xx·거절: 이 구간에서 관측되지 않았다. 실패는 러너 타임아웃이다.
- 하드웨어를 한 단계 키우는 것: 얇을 때는 캡·틱이 먼저고, 두꺼울 때는 호가 자료구조·만료가 먼저다. 코어를 늘려도 같은 종목 replica는 1개다.

## 5. 해석 한계

- 러너 생성 부하라 k6 `constant-arrival-rate`가 아니다.
- p99 ~220ms는 기본 히스토그램 버킷에 붙는다. 300–900ms로 올라간 09-17 꼬리만 버킷 밖으로 분명히 나간다.
- `orderbook_depth`는 종목·사이드별 잔량 합이다. 주문 건수와 1:1이 아니다.
- 09-16 17:12·19:10 급변은 배포로 호가가 비워진 구간이다. 설정 값이 초 단위로 바뀐 것이 아니다.
- RSS 815 MiB는 두꺼운 호가 + 두 프로세스의 단발 값이다. 누수 결론은 내지 않는다.
- `interval_seconds` 마이그레이션과 틱 250ms는 이 측정 기간에 로컬·GCE에 올렸고, 이 보고서 작성 시점에 Git `main`과 반드시 같지는 않다.

## 6. 다음에 재면 되는 것

1. 호가를 무한히 쌓지 않는 만료. 러너 DELETE가 밀려도 매칭기가 벽시계 TTL로 빼는지, 아니면 재시작으로만 비우는지를 먼저 가른다.
2. 틱 한 바퀴를 실제로 250ms 아래로 둘 수 있는지. 호가 GET을 틱 스레드 동기 경로에서 빼는 쪽이 타이머만 줄이는 것보다 먼저다.
3. 잔량을 고정한 채(또는 상한을 둔 채) 캡·틱만 바꿔 CPU 1.8–2.0에서 POST가 올라가는지 본다. 잔량이 같이 늘면 3.5와 같은 붕괴를 다시 본다.

큐, 멀티 replica, 머신 업사이즈는 아직 도입 조건이 아니다. 지금은 같은 2코어에서 호가가 두꺼워지면 처리량이 스스로 접힌다.
