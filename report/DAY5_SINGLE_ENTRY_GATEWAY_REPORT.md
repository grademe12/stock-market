# Day 5 단일 진입점 보고서

Day 4에서 VM을 `e2-standard-4`로 올린 뒤, 샤드를 `nproc`만큼 나누면 남는 2 vCPU를 쓸 수 있었다. 막힌 것은 매칭이 아니라 공개 포트였다. Tailscale ACL은 `:8000`·`:8001`만 열려 `:8002`·`:8003`은 미니 PC에서 타임아웃이고, 러너·프론트가 `/ready/`를 보고 포트를 골랐다. 종목 라우터를 `:8000`에 두고 matcher는 loopback만 듣게 바꿨다. 수치는 2026-09-18 16:20–09-21 16:10 KST Prometheus다.

**학습 질문**: 이용자는 URL 하나만 보는데, 같은 종목 호가창은 프로세스 1개로 유지할 수 있는가? 그 홉을 넣으면 접수 품질은 유지되는가?

## 1. 측정 조건

러너 설정은 Day 4와 같다. 바꾼 것은 진입점과 샤드 수, 스크레이프 경로다.

| 항목 | 값 |
|---|---|
| Backend | GCE `e2-standard-4`. 4 vCPU, 16 GiB. `isSharedCpu=false` |
| 공개 진입점 | `http://stock-market-gce:8000`. Python 종목 라우터. host network |
| 매칭기 | 샤드 4개. `127.0.0.1:8001`–`:8004`. 샤드마다 Gunicorn worker 1 · threads 4 |
| 분배 | 시뮬 10종목. `position % 4` → 3·3·2·2. 같은 종목 replica 없음 |
| 러너 | 미니 PC. noise 0–3 + momentum / mean_reversion / liquidity_provider. `event_reactive` 0 |
| 고정 캡 | `HTTP_CONCURRENCY=64`, `TICK_INTERVAL_MS=250`, `MAX_TRADERS=1000` |
| 경로 | 러너·프론트·Prometheus → `:8000`만. matcher 포트는 VM loopback |
| 관측 | 미니 PC Prometheus/Grafana. G4 이후 SD는 `:8000/metrics/{shard}/` |

컷오버는 매칭기 재시작이라 메모리 호가는 0부터다. 주문·체결·잔고는 비영속이다.

## 2. 이날 한 일

1. G1 라우터. `POST /orders/` 바디 `symbol`, 취소는 쿼리 `symbol`. 단위 테스트.
2. G2 배포. matcher `GUNICORN_BIND=127.0.0.1`, 공개는 게이트웨이 `:8000`.
3. G3 클라이언트. 러너·프론트에서 샤드 URL 확장 삭제. `BACKEND_BASE_URL` 하나.
4. 09-18 16:32 KST 실기 컷오버. 미니 PC에서 `:8001` 접속 거부, `:8002`–`:8004` 타임아웃, `:8000` 호가·주문 200.
5. G4. 게이트웨이가 `prometheus-sd`를 만들고 `/metrics/{n}/`·`/ready/{n}/`로 넘긴다. 16:40 전후 스크레이프 4개가 `up`.

ACL에 `:8002`–`:8003`을 열지 않았다. 일반 LB로 주문을 둥글게 뿌리는 것도 하지 않았다.

잔량 합은 3일 동안 0.8만–1.2만에 머물렀다. Day 4의 분당 +1.4만 직선이 아니다. 대신 RSS는 255 MiB에서 4.3 GiB로 거의 선형이다. 16 GiB의 약 1/4이다.

## 4. 병목

```text
[공개 :8000+N + ACL :8000-8001] --샤드 2·3은 미니 PC에서 안 보임-->
[종목 라우터 :8000] --이용자 계약은 유지, 같은 종목은 프로세스 1개-->
[4 matcher × loopback] --4 vCPU를 프로세스 수와 맞춤-->
[잔량 합은 평평] --취소가 신규 잔량을 따라감-->
[RSS만 증가] --호가 수량 게이지와 어긋남-->
```

### 4.1 돌아온 것: 진입점과 네 코어

이용자·러너·프론트·Prometheus는 `:8000`만 본다. 미니 PC에서 matcher 포트는 닫혀 있다. 주문은 종목으로 샤드를 고르므로 창이 갈라지지 않는다.

Day 4에서 CPU 합 1.94–1.98은 프로세스 두 개가 코어를 채운 값이었다. 지금은 프로세스 네 개가 각 0.2코어, 합 0.87이다. 4 vCPU의 약 22%다. 접수 146/s, p50 2.7ms, p99 19ms는 Day 4 55분 후(127/s, 37/100ms, 잔량 74만)보다 가볍다. 호가가 얇게 유지된 효과가 크다.

### 4.2 그대로인 것: 한 종목 한 프로세스, O(n) 창

매칭 알고리즘과 TTL 만료 위치는 그대로다. 잔량이 다시 두꺼워지면 Day 3·4와 같은 한 건 비용이 돌아온다. 게이트웨이는 그 비용을 나누지 않는다.

### 4.3 새로 보이는 것: 수량과 메모리

잔량 합이 평평한데 RSS가 하루 약 1.3 GiB씩 늘었다. `orderbook_depth`는 심볼·사이드 수량이다. 프로세스 힙에 남는 주문 객체·히스토리·할당은 이 게이지에 없다. 3일 창에서는 메모리가 CPU보다 먼저 벽에 닿을 후보다.

게이트웨이 프로세스 CPU는 Prometheus에 없다. 매처 `process_cpu`만 봤다.

## 5. 해석 한계

- 컷오버가 호가를 비웠다. “두꺼운 창 + 라우터 홉”은 이 창에 없다.
- POST 지연은 matcher Django 히스토그램이다. 러너가 겪는 Tailscale+게이트웨이 시간은 별도다. 러너 `request_failures`는 컷오버 직후 거의 0이었다.
- p99 ~19ms는 기본 버킷 아래라 Day 3의 220ms 고착과 비교하면 아직 싸다. 버킷 한계는 같다.
- 09-18 16:20의 POST 213/s는 스크레이프된 두 샤드 합이다. 막힌 샤드 부하는 이 시계열에 없다.
- Grafana CPU 패널은 컷오버 전 `:8000`·`:8001`과 이후 `:8000/shard/N`을 한 화면에 겹친다. 최근 15분이 4선이다.

## 6. 다음에 재면 되는 것

1. 러너를 늘렸을 때 잔량 합이 평평한 구간을 벗어나 p50이 다시 수십 밀리초로 가는지. 게이트웨이가 아니라 창 두께의 벽시계다.
2. RSS 기울기가 16 GiB에 닿는 시각. 수량 게이지가 안 오르면 만료·객체 수 쪽을 따로 봐야 한다.
3. 게이트웨이 프로세스 CPU. 주문이 늘면 매처보다 이 한 프로세스가 먼저 줄 수 있다.
4. 두꺼운 호가를 유지한 채 라우터만 끼우는 실험은 아직 없다. 재시작 없는 배포가 아니면 Day 4 리사이즈와 같이 효과가 섞인다.
