# Day 2 매처 샤드·처리량 보고서

[Day 1](DAY1_LOAD_BOTTLENECK_REPORT.md) 이후, 러너 HTTP 동시성 캡을 넣고 매처를 프로세스 2개로 나눈 구간이다. 수치는 2026-09-08 KST 운영에서 Prometheus와 러너 로그로 모았다.

**학습 질문**: 종목을 프로세스 두 개에 나누면 e2-medium의 vCPU 2개를 쓸 수 있는가. 그때 초당 주문은 같이 오르는가.

## 1. 측정 조건

| 항목 | 값 |
|---|---|
| Backend | GCE `e2-medium` (2 vCPU, 4 GiB), 컨테이너 2개, 각 Gunicorn worker 1 · threads 4, host network |
| 매칭기 | `SIMULATION_SHARD_COUNT=2`. 유니버스 상위 10종목을 거래대금 순위 교차로 5개씩 |
| 샤드 0 `:8000` | 000660, 009150, 002990, 005380, 105560 |
| 샤드 1 `:8001` | 005930, 402340, 005935, 006400, 012330 |
| DB | 미니 PC Postgres. 주문·체결은 비영속 |
| 경로 | 러너·프론트가 `matcher_shard`로 URL을 고름. 취소는 `?symbol=` |
| 관측 | Prometheus 타깃 `:8000`, `:8001` (재시작 후에야 둘 다 scrape) |
| 러너 | 전략 4컨테이너, `TICK_INTERVAL_MS=1000`, `MAX_TRADERS=1000`, `HTTP_CONCURRENCY` 16 후 32 |

`orders/s`는 샤드 합의 `POST /api/v1/orders/` 수다.

## 2. 이 구간에서 한 일

1. [PR #11](https://github.com/grademe12/stock-market/pull/11) 러너 주문·취소 HTTP를 `HTTP_CONCURRENCY`(기본 16)로 겹쳐 보냈다. 결정은 순차, 전송만 병렬이다.
2. [PR #12](https://github.com/grademe12/stock-market/pull/12) 매처를 컨테이너 2개로 나누고 종목을 교차 분배했다. Gunicorn `--workers 2`는 쓰지 않았다.
3. 배포 직후 샤드 1(`:8001`)은 Tailscale ACL이 `:8000`만 허용해 SYN이 GCE에 도착하지 않았다. 정책에 8001을 연 뒤에야 삼성전자·SK스퀘어 호가가 열렸다.
4. Prometheus는 설정에 8001이 있어도 리로드만으로는 타깃이 안 붙었다. 컨테이너 재시작 후 타깃 4개가 `up`이 됐다.
5. 유니버스 10종목 중 거래는 처음에 시드 5종목만 있었다. 나머지 5종목에 같은 수(전략 4 × 100)를 넣고 `MAX_TRADERS`를 1000으로 올렸다. 활성 프로필 4000명.

## 3. 부하 숫자

서버 측 지연은 Django 히스토그램이다. 러너 Tailscale 왕번복은 포함하지 않는다.

### 3.1 샤드 직후 · 거래 종목 5 (2026-09-08 19:30 KST 근처)

빈 호가 5종목(005935, 005380, 006400, 105560, 012330)에는 트레이더가 없었다.

| 지표 | 샤드 0 | 샤드 1 | 합 |
|---|---:|---:|---:|
| 주문 POST | ~71/s | ~48/s | ~120/s |
| HTTP 합계 | ~120/s | ~78/s | ~200/s |
| CPU | ~0.79 | ~0.55 | ~1.34 |
| 거래 종목 수 | 3 | 2 | 5 |
| 종목당 주문 | ~24/s | ~24/s | |
| POST p50 / p99 | 3.5 / 217 ms | 4.0 / 222 ms | |
| 4xx · 5xx · 거절 | | | 0 |

종목당 제출은 같았고, 샤드 부하는 산 종목 수 3:2를 따랐다. 담당 5:5와 실제 부하 5:5는 달랐다.

### 3.2 10종목 시드 후 · 동시성 16 (19:45 KST 근처)

| 지표 | 샤드 0 | 샤드 1 | 합 |
|---|---:|---:|---:|
| 주문 POST | ~62/s | ~63/s | ~126/s |
| HTTP 합계 | ~107/s | ~102/s | ~210/s |
| CPU | ~0.75 | ~0.67 | ~1.42 |
| 종목당 주문 | ~12/s | ~12/s | 10종목 |
| POST p50 / p99 | | | ~4 / 223 ms |

CPU와 주문률이 거의 같아졌다. 파이 크기는 5종목 때와 같고, 조각만 10개로 나뉘었다.

노이즈 러너 표본: 틱 10번에 약 133초(약 13초/틱), 틱당 주문 ~449. LP는 틱 10번에 약 4분.

### 3.3 동시성 32 (19:56 재시작 이후)

| 지표 | 값 |
|---|---|
| 주문 POST 합 | ~111/s (15분 `rate` 최소 99, 최대 143) |
| HTTP 합계 | ~190/s |
| CPU | 0.73 / 0.68 |
| POST p50 / p99 | ~4 / 226 ms |
| 노이즈 틱 10번 | 약 101초 (약 10초/틱), 틱당 주문 수는 16과 같음 |
| 러너 `request_failures` | 0 |

동시성을 두 배로 올려도 초당 주문은 오르지 않았다. 틱 벽시계만 조금 줄었다.

## 4. 병목

```text
[트레이더 결정] --1000명 순차, 아직 짧음-->
[호가 GET 종목 순차] --틱마다 10번-->
[러너 HTTP 캡 16→32] --서버 줄만 늘림-->
[Tailscale] --8001 ACL 누락이 한때 샤드 1을 죽임-->
[Gunicorn threads 4 × 프로세스 2] --동시에 실행되는 파이썬은 최대 8-->
[샤드당 GIL + 종목 RLock] --CPU 0.7대, 1.0 천장에는 못 감-->
```

### 4.1 샤딩이 한 일

프로세스 2개는 같은 종목을 복제하지 않고 집을 나눴다. 10종목이 거래하자 두 vCPU를 비슷하게 썼다(~0.7). 한 프로세스 GIL이 코어 하나만 쓰던 Day 1 후반의 “머신 절반 유휴”는 해소됐다.

`--workers 2`만 켜면 호가창이 두 벌이 된다. 이번 실험은 그 경로가 아니다.

### 4.2 샤딩이 안 한 일

초당 주문은 Day 1 안정화(~90–100/s)에서 ~120/s 근처로만 움직였다. 2배가 아니다. 트레이더 2000→4000도 종목당 제출을 반으로 나눴을 뿐 합은 같다.

틱은 컨테이너 전역 시계다. 사람 수를 늘리면 틱당 HTTP가 늘고 벽시계가 같이 늘어, 초당 건수는 거의 그대로다. Day 1과 같은 형태다.

### 4.3 동시성 32가 안 통한 이유

러너 4 × 32면 한 순간에 최대 128개가 들어간다. 백엔드는 프로세스당 스레드 4개라, 샤드당 동시에 돌아가는 요청은 네 줄이다. 나머지는 accept/락 대기이고 p50 4ms인 요청과 p99 220ms 꼬리가 같이 보인다.

Little의 법칙으로 보면 대기 줄만 길어지고 완료율은 안 오른다. CPU가 1.0이 아닌 것은 매처가 꽉 찬 게 아니라, 러너가 호가 조회·결정·1초 sleep을 섞어 보내기 때문이다.

캡 없이 1000 병렬은 Day 1과 같이 자기 부하 실패 형태다. 32는 그 전에 이미 수확 체감이 끝난 지점이다.

### 4.4 운영에서 드러난 것

- Tailscale 정책이 `:8000`만이면 샤드 1은 죽은 것과 같다. `infra/README.md` ACL을 `:8000, 8001`로 맞춰야 한다.
- Prometheus `--web.enable-lifecycle` 리로드가 새 static target을 안 읽은 적이 있다. 타깃 추가 후에는 프로세스 재시작을 확인한다.
- 메인 머지마다 backend 이미지가 다시 떠서 메모리 호가창은 비워진다. 장시간 RSS 증가(Day 1 ~2.6 GiB 후 프로세스 교체)는 이번 배포로 리셋됐고, 원인 결론은 아직 내지 않는다.

## 5. 해석 한계

- 제공 부하는 러너 틱이다. k6 고정 도착률이 아니다.
- 샤드 1 시계열은 Prometheus 재시작(19:31 KST 근처) 이전에는 없다. 그전 합계는 샤드 0만 본 값일 수 있다.
- p99는 버킷 보간이다. 평균 4ms와 같이 본다.
- e2는 공유 vCPU다. 게스트 CPU 0.7이 물리 코어 0.7은 아니다.
- 정규장 세션, 잔고, 체결 영속은 이 구간에 없다.

## 6. 다음에 재면 되는 것

1. 동시성 32를 더 올리기보다, 틱의 종목별 호가 GET을 겹치거나 러너 프로세스를 전략·샤드 단위로 나눈 뒤 주문/s와 CPU를 본다.
2. 러너 측 `urlopen` 히스토그램으로 서버 4ms와 클라이언트 왕복을 분리한다.
3. 제공 부하가 올라 CPU가 양쪽 0.9를 넘고 주문률이 멈출 때가 매처 2프로세스 천장이다. 지금은 그 숫자가 아니다.

큐와 Kubernetes는 이번에도 조건이 아니다. 종목 샤딩은 도입했고, 효과는 **CPU 분배**이지 **처리량 증가**가 아니었다.
