# Day 1 부하·병목 보고서

실습 관점에서 백엔드만 보지 않고, 러너·Tailscale·Postgres·매칭기를 한 경로로 본 첫날 기록이다. 수치는 2026-09-03~09-04 KST 운영 구간에서 Prometheus와 러너 로그로 모았다. [k6 기준선](../docs/LOAD_TEST_BASELINE.md)은 로컬 Compose·러너 없음·단일 종목 조건이라 같은 숫자로 직접 비교하지 않는다.

**학습 질문**: 종목을 늘리고 트레이더를 늘리면, 어디서 부하가 생기고 무엇이 처리량을 묶는가?

## 1. 측정 조건

| 항목 | 값 |
|---|---|
| Backend | GCE `e2-medium` (2 vCPU, 4 GiB), Gunicorn worker 1 · threads 4, host network |
| 매칭기 | 프로세스 1개, 종목별 인메모리 호가창, 종목당 `RLock` |
| DB | 미니 PC Postgres 17. 주문·체결·잔고는 비영속. 프로필·KRX 일별만 저장 |
| 경로 | 미니 PC 러너 → Tailscale → GCE:8000. GCE → Tailscale → 미니 PC:5432 |
| 관측 | 미니 PC Prometheus/Grafana, scrape `stock-market-gce:8000/metrics/` |
| 시뮬 유니버스 | `SIMULATION_SYMBOL_LIMIT=10`. 실제 시드는 상위 5종목 |
| 트레이더 | 4전략 × 5종목 × 100 = 활성 2000. `event_reactive` 0 |
| 러너 | 전략별 컨테이너 4개, `TICK_INTERVAL_MS=1000`, `MAX_TRADERS=500`, host network |
| 시드 종목 | 000660, 005930, 009150, 402340, 002990 (KRX 2026-09-02 거래대금 상위) |

`orders/s`는 `POST /api/v1/orders/` 201 수다. 러너 틱 수나 프로필 수가 아니다.

## 2. 하루 동안 바뀐 것

1. 멀티심볼 매칭기를 `main`에 올렸다. 첫 배포 두 번은 `migrate`가 Postgres에 붙지 못해 롤백됐다. 원인은 새 마이그레이션이 아니라, overlay 없이 `docker compose`를 써서 Tailscale `100.84.148.98:5432` 바인드가 사라진 것이다. 바인드 복구 후 배포는 성공했다.
2. 유니버스 10종목은 열렸지만 프로필 800명이 전부 `005930`이라 다른 종목 호가는 비어 있었다. 한 프로필은 한 종목만 본다. 멀티티커 의사결정은 없다.
3. 배포 직후 주문률이 ~104/s에서 ~46/s로 줄었다. 주문·호가·취소마다 `MarketDaily`를 Tailscale 너머로 다시 읽었기 때문이다. 주문 POST 평균 1.8ms → 38ms. [PR #9](https://github.com/grademe12/stock-market/pull/9)에서 기동 시 한 번 캐시하도록 고친 뒤 평균은 1.8ms로 돌아왔다.
4. 활성 프로필을 2000명으로 맞추고 러너 한도를 500으로 올렸다. 005930에 남아 있던 MR/LP 초과 400명은 비활성화했다.

## 3. 부하 숫자

서버 측 지연은 Django 히스토그램이다. 러너가 체감하는 Tailscale 왕복은 포함하지 않는다.

### 3.1 단일 종목 · 프로필 800 (시드 전, 러너 4개)

대략 09-03 이후 ~ 09-04 17:48 KST 전까지.

| 지표 | 값 |
|---|---|
| 주문 POST | ~103–107/s |
| 취소 DELETE | ~60–64/s |
| HTTP 합계 | ~165–170/s |
| 체결 | ~75/s |
| POST 평균 / p50 / p99 | ~1.8 / 2.5 / 5 ms |
| 프로세스 CPU | ~0.45–0.47 코어 |
| RSS | ~70 MiB(재시작 직후) → 장시간 가동 후 ~750 MiB |
| 4xx · 5xx · `orders_rejected` | 0 |

이 구간 거래는 `005930`만이다. HTTP 170/s가 전부 Tailscale을 타므로 미니 PC `tailscaled`은 `top` 기준 코어 1개의 15–36%를 썼다. 박스 전체는 4코어, load ~1.0, idle ~87%였다. `top` %CPU는 코어 1개 = 100%다.

### 3.2 핫패스 DB 조회 (캐시 전, 짧게)

| 지표 | 값 |
|---|---|
| 주문 POST | ~46–48/s |
| POST 평균 / p50 / p99 | ~38 / 38 / 50 ms |
| Postgres | 초당 트랜잭션 ~480, 마지막 쿼리는 `exchange_marketdaily` |
| `tailscale0` | 약 900–1300 pps |

주문 1건에 유니버스 확인이 두 번(`create_order`, `books.get`) 들어가고, 각각 `MarketDaily`를 두 번 읽었다. 러너 구성은 그대로인데 처리량이 반으로 줄었다. 캐시 배포 후 이 부하는 사라졌다. Postgres는 초당 약 2건(ready/`SELECT 1`)으로 돌아왔다.

### 3.3 5종목 · 프로필 2000 (시드·러너 재시작 후)

재시작 직후 약 3분(08:48–08:51 UTC)과 안정화 후(08:53 UTC~)를 나눈다.

| 지표 | 피크 (재시작 직후) | 안정화 후 |
|---|---|---|
| HTTP 합계 | ~270/s | ~160/s |
| 주문 POST | ~179/s | ~85–97/s |
| 취소 DELETE | ~100/s | ~59/s |
| 체결 | ~114/s | ~66/s |
| POST 평균 / p50 | 2.3 / 2.6 ms | 3.4 / 2.5 ms |
| POST p99 | 5–17 ms | 히스토그램상 ~130 ms |
| 프로세스 CPU | ~0.72 | ~0.82–0.85 |
| RSS | 750 → 932 MiB | ~930 MiB |
| ready / up | 1 | 1 |
| 4xx · 5xx · 거절 | 0 | 0 |

종목별 주문은 피크 때 초당 27–29건으로 고르게 나뉘었다. 다섯 호가에 잔량이 생겼다. 러너 `request_failures`는 0이었다.

p99 130ms는 초당 한두 건이 100–250ms 버킷에 들어간 꼬리다. 같은 1분 창에서 대부분 요청은 5ms 이하, 평균 3.4ms다. p99만 보고 전체가 느려졌다고 보지 않는다.

그래프가 치솟았다가 내려앉은 것은 장애가 아니다. 러너 4개가 동시에 기동하면서 첫 틱에 주문이 몰렸고, 이후 틱 벽시계가 늘어 제공 부하가 줄었다. 대시보드 “거절” 패널은 `orders_rejected`와 체결을 같이 그린다. 거절 시계열은 없었고 체결·취소가 같이 뛴 것이다.

## 4. 병목

경로를 앞에서부터 보면 지금 묶는 지점은 백엔드가 아니다.

```text
[트레이더 결정] --로컬, 짧음-->
[러너 동기 HTTP 한 줄] --여기가 현재 한도-->
[Tailscale] --항상 비용, 상시 30%는 이 구간-->
[Gunicorn 4 thread + 종목 RLock] --여유 있음, 다음 후보-->
[Postgres] --캐시 후 핫패스에서 제외-->
```

### 4.1 현재 한도: 러너 직렬 HTTP

틱은 컨테이너 1개의 전역 시계다. 루프는 `tick_once()`가 끝난 뒤에야 `TICK_INTERVAL_MS`(1초)를 쉰다. 1초마다 깨워서 일하는 메트로놈이 아니다.

한 틱 안에서 만료 취소·호가 GET·`next_intents()`·주문 POST가 모두 일어나고, POST/DELETE는 `urllib.request.urlopen` 한 건씩 대기한다. 전략 코드는 Intent만 만들고, 한 줄로 보내는 쪽은 러너 오케스트레이션이다.

시드 후 로그 표본:

| 러너 | 대략 틱 간격 | 틱당 주문 | 초당 주문 |
|---|---:|---:|---:|
| noise | ~9초 | ~225 | ~25 |
| momentum | ~10초 | ~220 | ~22 |
| mean_reversion | ~5초 | ~130 | ~26 |
| liquidity_provider | ~20초 | ~450 | ~22 |

트레이더를 전략당 100→500으로 늘리면 틱당 HTTP가 늘고 틱 벽시계가 같이 늘어, 초당 주문은 거의 그대로다. LP가 더 느린 것은 미체결 ~2000건의 취소를 주문보다 먼저 직렬로 보내서다.

재시작 피크 179/s, 당시 p99 5ms, 거절 0은 백엔드가 그 이상도 받을 수 있다는 증거다. 안정화 후 ~90/s로 내려간 것은 러너가 그만큼만 보내서다.

### 4.2 다음 후보: 단일 프로세스 매칭기

백엔드 CPU는 0.45에서 0.85 코어로 올랐다. 1.0에 가까워지면 GIL과 종목 `RLock`이 체감된다. worker를 2로 올리면 호가창이 쪼개지므로 이 구조에서는 답이 아니다.

캡 없이 러너 주문을 500 병렬로 열면, 권한 있는 정상 주문이지만 연결 폭주 형태는 자기 부하 테스트 실패·자기 DoS와 같다. 실습에서는 동시 전송 캡(16–32)을 두고 제공 부하를 재는 쪽이 맞다. 캡을 열면 병목은 바로 이 매칭기로 넘어갈 가능성이 크다.

### 4.3 항상 있는 비용: Tailscale

러너와 백엔드가 다른 기계에 있으면 HTTP 170/s가 암호화 경로를 탄다. DB 캐시 이후에도 `tailscaled` 30%대가 남은 이유다. 데몬 수명 평균 CPU는 1.6%라, 러너가 이 속도일 때만 보인다. 패킷 캡처는 직렬 여부와 클라이언트 RTT를 한 번 확인하는 용도로 충분하고, 상시 스택으로 둘 단계는 아니다. 상시가 필요하면 러너 쪽 `urlopen` 히스토그램이 맞다.

### 4.4 이미 닫은 것: 핫패스 Postgres

기동 시 유니버스 캐시 전, 주문 경로의 `MarketDaily` 조회가 처리량을 반으로 줄이고 Tailscale pps를 올렸다. 지금은 프로세스 메모리 집합만 본다. KRX import 스키마 충돌이 아니었다.

## 5. 해석 한계

- 러너 생성 부하라 k6 `constant-arrival-rate`가 아니다. 제공 부하가 틱 길이에 묶인다.
- 시계열은 15–30초 해상도의 `rate()`다. 재시작 직후 창은 피크와 공백을 평균한다.
- p99는 Prometheus 기본 버킷 보간이다. 꼬리 몇 건에 민감하다. 평균·버킷과 같이 본다.
- RSS 증가는 장시간 가동 + 호가·미체결 증가의 단발 관측이다. 누수 결론은 내지 않는다.
- 미니 PC에는 k3s, Grafana, Cursor도 있다. `tailscaled` %만으로 호스트 포화를 말하지 않는다.
- 정규장 세션 경계, rate limit, 잔고 검증, 체결 영속은 이 구간에 없다.

## 6. 다음에 재면 되는 것

1. 러너 전송 동시성 캡을 두고, 틱 벽시계와 주문률·백엔드 CPU·p99를 같이 본다.
2. 같은 캡에서 러너 측 HTTP 지연 히스토그램을 넣어 서버 3ms와 클라이언트 왕복을 분리한다.
3. CPU가 0.9를 넘고 주문률이 더 이상 안 오르면, 그때가 매칭기 한도를 수치로 남길 시점이다.

큐, 멀티 replica, 종목 샤딩은 아직 도입 조건이 아니다. 지금은 러너 제공 부하가 매칭기 한도보다 낮다.
