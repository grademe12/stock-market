## 3. 무엇을 바꿨나

| 동작 | 이전 | 이후 |
|---|---|---|
| 잔량 적재 | 리스트 append 후 전체 `sort` O(n log n) | 가격대 큐 끝에 추가. 새 가격대만 `bisect.insort` |
| 체결로 맨 앞 제거 | `list.pop(0)` O(n) | 가격대 큐 `popleft` O(1) |
| 취소 | 양쪽 리스트 순회 O(n) | 주문 ID 인덱스로 찾고 지연 삭제 O(1) |
| 조회 | 순회 O(n) | 인덱스 O(1) |
| 호가 스냅샷 | 모든 주문을 가격대로 합산 O(n) | 가격대별 수량 합을 읽기만. O(가격대 수) |
| 메트릭 갱신 | 요청마다 스냅샷 O(n) | 양쪽 수량 합 읽기 O(1) |

- 구조: 매수·매도 쪽마다 정렬된 가격 목록 + 가격대별 FIFO 큐 + 수량 합을 둔다. 주문 ID 인덱스와 쪽별 수량 합도 유지한다.
- 지연 삭제: 취소된 주문은 표시만 하고 큐 맨 앞에 올 때 버린다. 한 가격대에 죽은 항목이 64개를 넘고 산 것보다 많아지면 큐를 다시 만든다. 앞에 잘 오지 않는 가격대에서 메모리가 새지 않게 하려는 것이다.
- 레지스트리의 주문 ID → 종목 맵이 체결된 주문을 지우지 않고 있었다. 이제는 호가창이 알려 주는 적재·종료 콜백으로 관리한다. Day 5의 RSS 증가 원인 중 하나였을 것으로 보인다(추정).
- 새 메트릭: `orderbook_open_orders`(남은 주문 건수), `orders_expired_total`(만료 건수).
- matcher 쪽 만료(`MATCHER_ORDER_MAX_AGE_SECONDS`)를 추가했다. 호가창에 올라간 지 N초가 지난 주문을 다음 호출 때 지운다. 기본은 꺼짐이다. 5.2 참고.

## 5. 해석

### 5.1 악순환이 끊겼다

Day 6의 고리는 `잔량 증가 → 한 건 비용 증가 → 취소 지연 → 잔량 증가`였다. 이번에도 잔량은 계속 늘었다(18.8만 → 85.2만 건). 하지만 둘째 화살표가 사라졌다. 잔량이 4.5배가 되는 동안 POST p50은 2.6 → 2.7 ms, 주문 1건당 matcher CPU는 2.6 → 2.8 ms였다. 잔량이 늘어도 matcher는 느려지지 않으니 고리가 돌지 않는다.

주문/s는 590 → 555로 6% 줄었다. matcher 쪽 지연은 그대로이므로 matcher 밖(게이트웨이, 러너)의 변화로 본다(추정). 5.3 참고.

잔량이 계속 늘어난 것은 서버가 아니라 러너 쪽 사정이다. 러너가 TTL이 지난 주문을 취소하는 속도가 접수 속도를 따라가지 못했다. 종목 2개짜리 샤드를 맡은 noise-2/3은 남은 주문이 900개 안팎으로 취소를 따라갔다. 종목 3개짜리 샤드를 맡은 noise-0/1과 LP-0/1은 17만 – 39만 개가 쌓였다. 샤드별 matcher 지연은 같으므로, 러너 동시성 64개 안에서 주문과 취소가 경쟁한 결과로 보인다(추정).

### 5.2 matcher 만료 재측정(Run B)은 하지 않았다

계획에는 만료 120초를 켠 Run B가 있었다. 하지 않은 이유는 두 가지다.

1. **실제 거래소의 기능이 아니다.** 한국 정규장 주문은 당일 유효다. 체결되거나 취소되지 않으면 장 마감까지 호가창에 남고, 마감 때 일괄 소멸한다. 거래소는 "오래되면 버린다"로 잔량을 막지 않는다. 쌓여도 느려지지 않는 엔진, 유입 제한, 가격제한폭으로 막는다. 이 프로젝트의 만료는 `always_open`에 없는 장 마감 정리를 짧은 주기로 흉내 낸 대체물이다.
2. **Day 7 결론은 이미 Run A로 나왔다.** 하루치 잔량을 들고도 버티는 것은 만료가 아니라 자료구조가 한 일이다.

만료 기능은 단위 테스트로 검증했고, 코드에 기본 꺼짐으로 남긴다. 클라이언트가 취소를 보내지 않아도 서버가 스스로 정리할 수 있는 안전장치다.

### 5.3 다음 병목: 게이트웨이

| 근거 | 값 |
|---|---|
| 게이트웨이 CPU | 104 – 118%. 단일 Python 프로세스의 실질 상한(사용자 코드 1코어 + 소켓 처리) |
| VM 여유 | idle 14 – 21%. 코어가 모자란 것이 아니다 |
| matcher | 샤드당 31 – 48%. 여유 있음 |
| 러너 슬롯 | 컨테이너마다 `http_in_flight=64`로 항상 가득 |
| 러너 체감 지연 | 리틀의 법칙: 동시 요청 640 ÷ 초당 요청 약 840 ≈ 0.76초. matcher 안에서 쓰는 시간은 2.7 ms |
| TIME_WAIT | 2.2만 → 4.9만. 게이트웨이가 matcher에 요청마다 새 연결을 여는 것으로 보인다(추정) |

0.76초 중 대부분이 matcher 밖에서 쓰인다. 게이트웨이는 메트릭이 없어 대기열 길이를 직접 볼 수 없다. 그래서 "게이트웨이 대기"는 CPU 포화와 리틀의 법칙에서 끌어낸 추정이다. 이 추정은 5.4에서 메트릭을 붙여 확인했다.

게이트웨이를 다른 VM으로 옮겨도 이 상한은 그대로다. 막는 것은 VM 코어가 아니라 프로세스 1개다. 순서는 관측 → 연결 재사용 → 프로세스 여러 개(`SO_REUSEPORT`) → 분리다. 게이트웨이는 상태가 없어서, 세 번째가 Day 9 후보인 "stateless 게이트웨이 확장"과 같다.

### 5.4 후속 확인 (11-05): 기다리는 곳은 게이트웨이 앞의 커널 대기열이다

5.3의 추정을 확인하려고 게이트웨이에 자체 메트릭을 붙였다(PR #32, `9e49ef3`, [`gateway/README.md`](../gateway/README.md)). 같은 러너 조건으로 11-05 22:55 – 23:15 KST에 20분 돌렸다. 원본은 [`data/day7/gateway-metrics-check.txt`](data/day7/gateway-metrics-check.txt)다.

| 구간 | 값 |
|---|---|
| 커널 접속 대기열 `gateway_listen_queue` (15초 표본 67개) | p50 12, p90 193, 최대 363 |
| `accept()` 뒤 처리 스레드 시작까지 p99 | 2.4 ms |
| 게이트웨이 안 POST p50 / p99 | 9.4 ms / 100 ms |
| 그중 matcher 왕복 p50 | 7.6 ms |
| 게이트웨이가 처리 중인 요청 (10분 평균) | 11 |
| 게이트웨이 CPU / 요청 | 1.09 코어 / 846건/s |
| 미니 PC → 게이트웨이, matcher에 가지 않는 400 요청 30회 | 연결 p50 5.7 ms, 첫 바이트 p50 222 ms, p90 400 ms |

마지막 줄이 결정적이다. 게이트웨이 안에서 1 ms도 걸리지 않는 요청이 첫 바이트까지 0.2 – 0.4초 걸렸다. 네트워크 왕복은 3 ms다. 시간은 연결이 받아들여지기 전에 쓰인다.

해석은 다음과 같다.

1. 러너 11개가 250ms 틱마다 요청을 한꺼번에 보낸다. 연결이 수백 개씩 몰려 온다.
2. 게이트웨이는 스레드 하나가 연결을 하나씩 `accept()`하고, 그 스레드도 처리 스레드들과 GIL을 나눠 쓴다. 초당 약 850개가 이 구조의 상한이다.
3. 300개가 몰리면 다 꺼내는 데 약 0.35초다. 그동안 연결은 커널 대기열에 있다.
4. 게이트웨이 안에서 재는 시간(9 ms)에는 이 대기가 들어가지 않는다. 처리 시간만 보면 멀쩡해 보이고, 대기열 길이를 같이 봐야 보인다.

그래서 5.3의 결론(게이트웨이 단일 프로세스)은 맞고, 기다리는 위치가 게이트웨이 안이 아니라 앞이라는 점이 더해졌다. 해결 순서도 같다. `accept()`를 여러 프로세스로 나누는 `SO_REUSEPORT`가 가장 직접적이다.

설명하지 못한 부분이 남는다. 러너 동시 요청으로 계산한 0.76초와 직접 잰 0.22초(p50)의 차이다. 러너에는 요청 시간 지표가 없다. 미니 PC CPU 압력이 약 30%여서 러너 쪽 대기일 수 있다(추정).

## 6. 해석 한계

- 실행 시간이 2시간 41분이다. 계획은 6시간이었다. 잔량 4.5배 구간에서 지연이 평평했고, 같은 잔량의 Day 6 상태를 이미 넘어서 중단했다. 더 긴 시간에서만 보이는 현상(예: 객체 수 증가에 따른 GC 정지)은 확인하지 않았다.
- RSS는 남은 주문 1건당 약 1.1 KiB로 늘었다(추정: RSS 증가 ÷ 남은 주문 증가). 시간당 약 0.33 GiB로, 6시간이면 약 2.4 GiB다. VM 16 GiB 안이다. 장시간 기준선이 아니라 외삽이다.
- POST 지연은 matcher Django 히스토그램이다. 게이트웨이·Gunicorn 대기 시간은 없다.
- 게이트웨이와 VM CPU는 5분 간격 Run Command 순간값이다. 샘플러가 14:48에 작업 세션 종료와 함께 멈춰서 이후는 15:19 1개뿐이다.
- Prometheus의 `sum(runner_http_in_flight)`는 170 – 357로, 러너 로그의 컨테이너당 64와 맞지 않는다. 리틀의 법칙에는 러너 로그 값을 썼다.
- 마이크로벤치는 단일 스레드 순수 Python이다. 가격 모델(기준가 ±20호가, 수량 1 – 15)은 러너 프로필을 흉내 낸 것이고 실제 분포와 다르다.
- 무작위 비교 테스트는 옛 구현과 "같다"는 것만 보장한다. 옛 구현에 있던 규칙상의 오류가 있다면 그대로 이어진다.
- 러너 미니 PC는 CPU idle 38%이지만 CPU 압력(PSI some)이 약 35%였다. 러너가 한계는 아니지만 완전히 여유 있는 상태도 아니다.
- Day 6의 러너 중복 취소 경합(`symbol is required` 400)은 조건을 같게 하려고 고치지 않았다.
