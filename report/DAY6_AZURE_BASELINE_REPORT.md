# Day 6 Azure 기준선 · 매칭기 포화 보고서

GCP 무료 체험이 끝나 백엔드 VM을 Azure로 옮겼다. 로드맵 E1(호가창 비용 개선)의 "변경 전" 기준선을 새 VM에서 잡는 것이 목적이었다. 측정 도중 게이트웨이 접속 대기열이 먼저 막혀 있는 것을 찾았고, 그것을 고친 뒤에는 Day 3 패턴이 훨씬 빠르게 재현됐다. 수치는 2026-11-02 16:50 – 11-03 17:47 KST Prometheus와 VM 샘플이다. 원본은 [`data/day6/`](data/day6/)에 있다(VM 샘플, 수정 전 Prometheus 추이, 러너 최종 상태, 샘플러·조회 스크립트).

**학습 질문**: 같은 러너 부하에서 어느 구간이 먼저 한계에 닿는가? 그 병목은 하드웨어로 풀리는 종류인가, 다른 레버가 필요한 종류인가?

## 4. 병목

```text
[게이트웨이 backlog 5] --연결 거절 770/s, 재전송 대기-->
(수정) [게이트웨이 CPU 80%] --잔량이 쌓이며 matcher 한 건 비용 증가-->
[matcher 4개 × 1코어 포화] --같은 CPU로 처리 건수 약 1/16-->
[취소도 같은 대기열] --잔량 정리 지연-->
[잔량 증가] --다시 한 건 비용 증가-->
```

### 4.1 병목이 옮겨 간 순서

| 시점 | 처리량 | 먼저 한계에 닿은 곳 | 근거 |
|---|---|---|---|
| 수정 전 | 주문 약 290/s | 게이트웨이 접속 대기열(5) | overflow 770/s, matcher 내부 지연은 수 ms |
| 수정 직후 | 주문 약 550/s | VM CPU, 그중 게이트웨이 단일 프로세스 | idle 4.8%, gateway 약 80% |
| 1시간 뒤 이후 | 주문 344 → 22/s | matcher | matcher 4개 각 91–100%, gateway 0.5–9% |

설정 한 줄로 접수량이 거의 두 배가 됐다. 그 결과 잔량이 더 빨리 쌓였고, 병목은 matcher로 넘어갔다. 이후 20시간은 matcher가 병목이었다.

### 4.2 matcher: 더 일해서가 아니라 한 건이 비싸져서

matcher CPU 합은 21:11 3.06에서 이후 3.7–3.9로 거의 일정하다. 같은 CPU로 처리한 주문은 344/s에서 22/s로 줄었다. CPU 증가분까지 넣으면 주문 한 건에 드는 CPU가 약 19배가 됐다. 그사이 바뀐 것은 잔량(109만 → 641만 주)이다.

`backend/exchange/orderbook/book.py`와 `views.py` 기준으로 잔량에 비례하는 연산은 다음과 같다.

| 동작 | 지금 | 비용 |
|---|---|---|
| 잔량 적재 `_rest` | 리스트 append 후 전체 `sort` | O(n log n) |
| 체결로 맨 앞 주문 제거 | `list.pop(0)` | O(n) |
| 취소·조회 | 양쪽 리스트 순회 | O(n) |
| 호가 스냅샷 | 모든 주문을 가격대로 합산 | O(n) |
| **메트릭 갱신** `_update_orderbook_depth` | **모든 주문·취소 뒤에 스냅샷 호출** | **요청마다 O(n)** |

마지막 줄이 이번에 새로 확인한 것이다. 관측용 게이지를 갱신하는 일이 요청마다 호가창 전체를 훑는다. 위 연산 중 어느 것이 CPU를 가장 많이 쓰는지는 아직 재지 않았다.

샤드는 프로세스 1개라 GIL 때문에 1코어가 상한이다. 각 샤드가 91–100%이므로 이 구조에서 더 받을 여유가 없다.

### 4.3 악순환: 정리도 같은 길로 간다

러너는 TTL이 지난 주문을 DELETE로 지운다. 취소도 주문과 같은 matcher 스레드 4개에서 기다린다. 그래서 `잔량 증가 → 한 건 비용 증가 → 취소 지연 → 잔량 증가`가 이어진다. matcher에는 자체 만료가 없고, `always_open`이라 세션 마감 정리도 없다.

### 4.4 응답을 못 받은 주문이 잔량을 더 키웠다

러너가 timeout으로 포기한 요청도 서버에는 도착해 처리된다. 접수 335.7만 중 약 120만은 러너가 응답을 받지 못했다. 그 주문 ID를 모르므로 러너는 취소하지 않는다. 체결되지 않은 것은 호가창에 계속 남는다. 22:45 이후 matcher 접수율과 러너 성공률의 차이가 점점 벌어졌다(83 대 75 → 22 대 6.8).

### 4.5 관측이 가장 필요할 때 끊겼다

Prometheus가 `/metrics`를 긁는 요청도 같은 matcher 스레드 4개에서 기다린다. 22시 무렵부터 스크레이프가 5초 timeout에 걸리기 시작했고, 11-03 오후에는 성공률이 27–32%였다. 실패한 샤드가 `sum(orderbook_depth)`에서 빠져 잔량이 줄어든 것처럼 보이는 구간이 있었다. 샤드별 `last_over_time`으로 보면 잔량은 한 번도 줄지 않았다. matcher 재시작도 0회였다.

### 4.6 수직 확장은 이 병목의 긴급 레버가 아니다

장애 중에는 코드 수정·재배포보다 서버를 키우는 것이 위험이 적어 보인다. 상태가 없고 요청을 병렬로 처리하는 일반 웹 API라면 그렇다. 이 matcher는 두 조건이 맞지 않는다.

| 조건 | 일반 웹 API | 이 matcher |
|---|---|---|
| 키우면 빨라지나 | 코어에 비례 | 샤드당 프로세스 1개, GIL로 1코어 상한. 코어를 늘려도 샤드 하나는 빨라지지 않는다. 코어당 성능이 좋아지면 일부 개선되지만 잔량 비례 비용이 곧 따라잡는다 |
| 키우는 동안 유지되나 | 무중단 교체 가능 | Azure VM 크기 변경은 재부팅이다. 호가창은 메모리에만 있어 모든 주문이 사라진다. 장중이면 거래 중단이다 |

실제 거래소의 과부하 대응도 서버 증설보다 미리 만들어 둔 운영 장치가 먼저다. 주문 유입 제한(throttling), 거래 일시 정지·서킷 브레이커, 일괄 취소(mass cancel)다. 이 장치들은 재시작 없이 걸 수 있지만 장애 전에 만들어 둬야 한다.

| 구분 | 무엇 | 끊는 고리 |
|---|---|---|
| 긴급 | 유입 제한, 잔량 임계치 초과 시 신규 주문 거절 | 입력 |
| 긴급 | 일괄 취소, 세션 마감(`scheduled`) | 쌓인 잔량 |
| 단기 | E1 호가창 자료구조 | 잔량 → 한 건 비용 |
| 단기 | matcher 쪽 주문 만료 | 정리를 클라이언트에만 의존 |
| 중기 | 연결 재사용, 게이트웨이·matcher 구조 | 다음 병목(요청당 고정 비용, 게이트웨이 1코어) |
| 그 뒤 | 샤드 추가, 더 큰 VM | 알고리즘이 효율적일 때 투입한 만큼 늘어난다 |

Day 4 결론("하드웨어는 시간을 벌 뿐")과 같은 방향이다. 이번에는 왜 그런지 구조로 설명할 수 있다.

## 5. 해석 한계

- POST 지연은 matcher Django 히스토그램이다. Gunicorn·게이트웨이 대기열에서 기다린 시간은 없다. 러너 체감 지연은 리틀의 법칙 추정과 curl 표본뿐이다.
- p50이 0.25–0.5s, p99가 1–2.5s 버킷에 들어간 뒤는 버킷 보간 값이다. 실제 분포와 차이가 클 수 있다.
- 11-02 22시 이후 스크레이프 성공률이 떨어져, 게이지(잔량, RSS)는 마지막 성공 값이고 카운터 비율은 성공한 스크레이프 사이의 증가량이다.
- `orderbook_depth`는 주문 건수가 아니라 남은 수량 합이다. 주문당 평균 수량(약 8)으로 나누면 종료 시 약 80만 건으로 추정된다.
- 게이트웨이 CPU와 VM 전체 CPU는 Prometheus에 없다. 5분 간격 Run Command 순간값이고, 04:45 – 17:47 사이 샘플이 없다.
- 수정 전 구간 VM 값은 순간값 2회뿐이다(19:37, 20:48 전후).
- 러너 쪽 중복 취소 경합이 있었다. 같은 주문에 취소가 두 번 나가 두 번째가 `symbol is required`(400)로 실패한다. 컨테이너당 수십 건이라 숫자에 주는 영향은 작다.
- 수정 전 구간 후반에 샤드 0은 이미 98.7%(순간값)였다. 수정 전에도 matcher 포화가 다가오고 있었다.
- 같은 VM에 게이트웨이·matcher·tailscaled가 함께 있어 CPU를 나눠 쓴다.
