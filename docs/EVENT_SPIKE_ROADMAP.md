## E1 — Day 6: 호가창 한 건의 비용 줄이기

### 현재 구조 (`backend/exchange/orderbook/book.py`)

| 동작 | 지금 | 비용 |
|---|---|---|
| 잔량 적재 `_rest` | 리스트에 append 후 매번 전체 `sort` | O(n log n) |
| 취소 `cancel`, 조회 `get_open_order` | 양쪽 리스트를 앞에서부터 순회 | O(n) |
| 호가 스냅샷 `_levels` | 모든 주문을 순회해 가격대로 합산 | O(n) |
| 만료 | 매칭기에 없음. runner의 DELETE에만 의존 | 취소가 밀리면 잔량이 계속 증가 |

Day 3에서 잔량이 190만까지 쌓이자 CPU는 1.5 → 1.9로 올랐는데 초당 주문은 139 → 17건으로 떨어졌다. 매칭 자체가 아니라 위 표의 적재·취소·스냅샷 비용이 원인이다.

### 바꿀 것

1. 가격대별 FIFO 큐 + 정렬된 가격 목록으로 바꾼다. 적재는 해당 가격 큐 뒤에 붙이고, 새 가격대만 정렬 위치를 찾는다(`bisect`).
2. 주문 ID → 위치 인덱스(dict)를 둬서 취소·조회를 O(1)에 가깝게 한다.
3. 가격대별 수량 합을 유지해 스냅샷이 주문 수가 아니라 가격대 수에 비례하게 한다.
4. (선택) 매칭기 쪽 만료: 주문에 만료 시각을 두고, 매칭·조회 시점에 만료된 주문을 걷어낸다. runner DELETE가 밀려도 잔량이 무한히 늘지 않게 한다.

가격·시간 우선, 부분 체결, maker 가격 체결 규칙은 바꾸지 않는다. 기존 단위 테스트가 그대로 통과해야 한다.

### 측정

- 같은 기계, 같은 runner 설정(Day 3 후반: 동시성 64, 틱 250ms, `MAX_TRADERS=1000`)으로 **변경 전 → 변경 후**를 각각 6시간 이상 돌린다.
- 보는 지표: `orderbook_depth` 합, 주문 POST/s, POST p50/p99, 프로세스 CPU, RSS, runner 타임아웃.
- 보조로 잔량을 고정한 마이크로벤치(잔량 1만/10만/100만에서 주문 1건·취소 1건·스냅샷 1건 시간)를 남긴다.

### 판정 기준

- 변경 전: 잔량이 늘수록 p50이 커지고 POST/s가 떨어지는 Day 3 패턴이 재현되어야 한다(재현이 안 되면 환경 차이부터 기록).
- 변경 후: 잔량이 같은 수준일 때 p50과 POST/s가 잔량 크기에 거의 영향을 받지 않아야 한다.
- 만료를 넣었다면: 6시간 동안 잔량 합이 평형에 머물러야 한다.

### 비목표

- 매칭 엔진의 다중 replica, 큐 도입, 주문 영속화.

## E2 — 재생 실험: 실제 공시를 원하는 시각에 다시 쏘기

### 왜 필요한가

실제 장에서 큰 공시는 언제 올지 모른다. 일주일을 돌려도 의미 있는 spike가 없을 수 있다. 실제 공시를 **녹화해 두고 재생하면** 같은 조건으로 여러 번 잴 수 있다.

### 바꿀 것

1. market-event-analyzer가 거래소로 보낸 `MarketEvent`를 파일(JSONL)로도 남긴다. 원본 공시 ID, 해석 결과, 방향, 강도, 보낸 시각을 포함한다.
2. 재생 도구: 녹화 파일을 읽어 `POST /api/v1/events/`로 다시 보낸다. 옵션은 시작 시각, 배속, 특정 이벤트만 선택.
3. 이벤트 ID는 재생마다 새로 만든다(멱등 키 충돌 방지). 원본 ID는 메타데이터로만 남긴다.

### 측정

- 평상 부하(E1 이후 설정) 위에 녹화 이벤트 1건 → 3건 동시 → 10분에 10건 순으로 재생한다.
- 보는 지표: 이벤트 수신~runner ack까지 지연, 이벤트 반응 트레이더의 주문 수와 시간 분포, 해당 종목 샤드의 POST/s·p99·CPU, 다른 샤드에 대한 영향(격리 여부).

### 판정 기준

- spike 동안 해당 종목 샤드 p99와 5xx, runner 타임아웃을 기록하고, **다른 종목 샤드의 지연이 함께 나빠지지 않는지**를 본다. 종목 단위 샤딩의 격리 효과가 이 실험의 핵심 질문이다.
- 같은 재생을 3번 반복해 결과가 비슷한지 확인한다.

## E3 — 실전 운영: 정규장 시간에만 켜고 실제 공시 받기

### 운영 방식

- 평일 08:50에 matcher·router·runner·analyzer를 올리고, 15:40에 내린다. systemd timer(또는 cron)로 자동화한다. 장 밖에는 아무것도 돌지 않는다.
- 기간은 1~2주. 휴장일은 KRX 영업일 기준으로 건너뛴다.
- 장외 시간에 들어온 공시는 [정규장 세션 계획](./REGULAR_MARKET_SESSION_PLAN.md)의 규칙대로 처리한다. 운영 전에 그 동작(보류 후 개장 시 전달인지, 만료인지)을 코드에서 확인하고 이 문서에 적는다.

### 측정

- E2 지표 전부 + 하루 단위 요약(공시 수, 이벤트 수, 반응 주문 수, 최대 spike 구간).
- **비용:** 공시 1건당 분석기 LLM 토큰과 비용, 하루 합계. 장 시간만 운영했을 때의 전력·장비 외 비용은 LLM 호출뿐이다.

### 판정 기준

- 실제 공시로 생긴 spike 중 가장 큰 구간을 골라, E2 재생 결과와 같은 패턴인지 비교한다.
- 실전에서만 생긴 문제(장외 이벤트 처리, 분석기 지연, 공시 원문 다운로드 실패 등)를 따로 기록한다.
